# Contracts between plugins

Every format, file, command or name that one plugin produces and another reads. Each has one
owner, who alone writes it and versions it. A contract typed in `core` lives in one module;
another language reads it as the JSON `npm run core` writes from that module. The column
« Target » says what program goal 4 turns each one into. A coupling absent from this table is a
defect.

| Contract | Owner | Read by | Today | Target |
|---|---|---|---|---|
| Measure file (`measure/<session>.json` under the orchestrator's module directory): fill, window, model, the session's `start` (its first figure, the brief it started on and its size) | orchestrator | bugs-bot (`gate --measure`, `bugs_bot/gate.py`) | untyped JSON, written and parsed in `hooks/gauge-core.ts`; bugs-bot re-implements the gate's thresholds in Python, and statusbar reads no measure file: it re-derives the gate in bash from `ORCHESTRATOR_CONTEXT_GATE*` | typed in `core`; statusbar shows the owner's `past_gate` instead of recomputing it |
| Plan state file (`IMPLEMENTATION.md`): header, `\| phase \| title \| status \| milestone \|` rows | method | implement (orchestrator to come) | **typed in core** (`method.ts`: `parseState`, `markRow`, `nextRow`); format in `plugins/method/skills/lifecycle/references/plan.md` | the orchestrator's plans read through the same functions |
| Report status line (`status: done\|blocked\|question — …`) | method | implement (orchestrator's relay to come) | **typed in core** (`method.ts`: `reportStatus`); implement's skills end on it | the orchestrator's `parseStatus` replaced by `reportStatus` |
| `deck.json` | orchestrator | Stream Deck (outside) | versioned JSON, a view of the state store held byte for byte by a golden test; each session writes it only when it differs from the file, and the minute's refresh is the machine's (orchestrator 0.98.11) | the same format, a view of the state store, one writer, rate-limited |
| Session name shapes (`Orch:`, `Agent:`, `Audit:`, `Coord:`; the former `Orch :` still read) | orchestrator | statusbar, bugs-bot, implement | defined in `core` (`names.ts`: `parseSessionName`, `sessionName`, `currentSessionName`), read there by implement and the orchestrator's `dispatch-record.ts`, `hooks/naming.ts`, `hooks/stop-gate.ts` and `sleeping.ts`; still re-implemented in the orchestrator's `hooks/move.ts`, `hooks/session-name.ts`, `iterm_agent.py`, `coordinator.sh`, bugs-bot's `hooks/core.ts` and statusbar's `statusline.sh` | one definition in `core`, read by every plugin |
| Round files (`round/*.json`): questions, answers | orchestrator | the orchestrator alone | private; github no longer reads them (github 0.18.0, orchestrator 0.99.0) | private |
| Consent records (`consents/<owner>/<name>/<entry>.json`): the operator's answer to a round question that asks their consent, the question, the subject (repository, pull request, `e2e-waiver`, `e2e-exemption` or `auto-merge`) its sender declared with `declare_wait`, the time | orchestrator | github (E2E waivers and exemptions, `auto-merge-set`) | **typed in core** (`consent-record.ts`, version 1); written by the pane's answer, the operator's answer typed in the asking session's own tab (`by: 'tab'`) and `round-close`, read by github in place of `round/` | the same |
| PR records (review, norms, e2e) | github | orchestrator, norms, pr-review | **typed in core** (`pr-record.ts`, version 1), the producer of each kind declared there, and the orchestrator's `accepted` review over a failed one at the same head (`ACCEPTANCE`, github 0.20.0, orchestrator 0.103.0), so github names no consumer; github's Python writer loads the generated `pr-record.json`; tested across both (`scripts/contracts.test.ts`); the review verdict is computed from the review agents' findings blocks (pr-review 0.7.0); github refuses a review record written by the session that pushed the head (github 0.14.0), and implement launches its reviewer as another session (`/implement:review`, 0.5.0) | the pushed heads known across sessions and machines, not only by the session that pushed |
| `mcp__github__gh` commands (`pr-create`, `pr-gate`, `pr-readiness`) and the `mcp__github__record` tool | github | orchestrator, norms, pr-review | declared by norms and pr-review (`>=0.20.0`, when the record tool took `dir`) and the orchestrator (`>=0.20.0`); a record written and a `pr-gate` or `pr-checks` read put `Ready` when the four hold (github 0.19.0), so the orchestrator runs `pr-gate` when its CI watch says green: `ci-watch.sh`'s green line ends with that call, `next: mcp__github__gh pr-gate {"pr": <n>}` (« What the caller does ») | the same |
| Launcher CLI (`iterm-agent.sh spawn`) | orchestrator | bugs-bot, implement, telemetry (`spawn` and `close` command lines read from the Bash calls it observes: `--title`, `--tier`, `--model`, `--effort`, `--permission-mode`, `--auditor`, `--coordinator-successor`; `hooks/collect.ts` `orchestrationOf`) | implement locates the orchestrator through the host's install record (core `recordedInstallPaths`), bugs-bot through its own reader of that record (`bugs_bot/plugin_path.py`); both hard-code the script's path inside the plugin | a declared command with a versioned argument set |
| Launcher bench opening (`iterm-agent.sh bench-open`, `close --bench --socket`) | orchestrator | the outcome evals (`scripts/lib/outcome`) | `bench-open` prints `socket=`, `tty=` and `session=`; `close --bench` ends the home server it names; both refuse a directory or a socket outside the bench the caller passes; the home server's socket (under `<bench>/tmux`) and the orchestrator's working directory sit inside the bench, while the launch script, the prompt, the servers' file and `close.log` go to the launcher's state directory | a declared command with a versioned argument set |
| Declared wait in a session's transcript (`declare_wait` tool call with `{kind, blocks}`, plus `question` for an `operator` wait, kinds `operator`, `tool`, `done`, `deferred`), and the `Decision: <question> → <choice>` lines the outcome evals' brief asks of an orchestrator | orchestrator | the outcome evals (`scripts/lib/outcome/transcript.ts`) | the tool's name and kinds are re-declared in `transcript.ts`, as the orchestrator's `hooks/wait.ts` and `stop-gate.ts` declare them; the `Decision:` line is the brief's own convention (`orchestration.ts`) | the kinds typed in `core`, read by both |
| Dispatch record command line (`dispatch-record.sh <sub> <record> [<id>]` and its `--class`, `--tier`, `--model`, `--effort`, `--head`, `--verdict`) | orchestrator | telemetry (read from the Bash calls it observes, `hooks/collect.ts` `orchestrationOf`) | the subcommand set documented in the header of `dispatch-record.sh`, re-read as words; an unknown subcommand is recorded as given | the record's events published by its owner |
| `ListAgents` text | host | bugs-bot | parsed by regex | the host's structured data, or a `core` parser owned once |
| Environment: `ORCHESTRATOR_SPAWNED`, `ORCHESTRATOR_CONTEXT_GATE*`, `CLAUDE_GITHUB_ROOT` | orchestrator / github | norms, statusbar, telemetry (`ORCHESTRATOR_SPAWNED`) | **named in core** (`env.ts`); `npm run deps` refuses another plugin's variable core does not declare; norms reads `ORCHESTRATOR_SPAWNED` through `isSpawned` | statusbar reads the gate from the measure file instead of the variables |

## Installer permission rules

The rules an installer writes (conventions, « Permissions and security »). Each names its own
script, which validates every argument.

| Rule | Plugin | Validation the script performs |
|---|---|---|
| `Bash(<install>/skills/iterm-agents/scripts/iterm-agent.sh spawn --open *)` | orchestrator | permission mode in an allowlist (program, orchestrator defect D2), directory checks |
| `Bash(bugs-bot:*)`, printed for the operator to add, never written (`bugs_bot/doctor.py` `ALLOW_RULE`) | bugs-bot | the CLI's own parser: one of its fixed subcommands; `deploy_check` still runs the project's command with `shell=True`, and only when the project file is the operator's alone (`bugs_bot/agent.py`) |
