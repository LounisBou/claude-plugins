# Contracts between plugins

Every format, file, command or name that one plugin produces and another reads. Each has one
owner, who alone writes it and versions it. A contract typed in `core` lives in one module;
another language reads it as the JSON `npm run core` writes from that module. The column
« Target » says what program goal 4 turns each one into. A coupling absent from this table is a
defect.

| Contract | Owner | Read by | Today | Target |
|---|---|---|---|---|
| Measure file (`measure/<session>.json` under the orchestrator's module directory): fill, window, model, the session's gate in tokens (`gate_tokens`), the session's `start` (its first figure, the brief it started on and its size); and the context gate's defaults and rule | orchestrator | bugs-bot (`gate --measure`, `bugs_bot/gate.py`), statusbar (`statusline.sh`) | **typed in core** (`orchestration.ts`, version 1: `MeasureReading`, `measureFilePath`, `parseMeasure`, `GATE_PERCENT`, `GATE_TOKENS`, `gateTokensOf`, `tripGate`), written by the orchestrator's `hooks/gauge.ts`; bugs-bot and statusbar read the path and the gate's percentage from the generated `orchestration.json`, and statusbar shows the file's `gate_tokens` | the same |
| Plan state file (`IMPLEMENTATION.md`): header, `\| phase \| title \| status \| milestone \|` rows | method | implement (orchestrator to come) | **typed in core** (`method.ts`: `parseState`, `markRow`, `nextRow`); format in `plugins/method/skills/lifecycle/references/plan.md` | the orchestrator's plans read through the same functions |
| Report status line (`status: done\|blocked\|question — …`, and `status: waiting — …` while an agent's own background work runs) and the machine line a message ends on (`machineLine`: its markup dropped) | method | implement, orchestrator (`hooks/relay.ts` `parseStatus` maps it to a wait, `hooks/agent-stop.ts`, `hooks/stop-gate.ts`) | **typed in core** (`method.ts`: `reportStatus`, `machineLine`); implement's skills end on it, and the orchestrator reads it through these two, with no parser of its own | the same |
| Operator question block (`**Question i of N**` and its labelled fields, lettered choices and recommendation; format in `plugins/method/skills/lifecycle/references/questions.md`) | method | orchestrator (`hooks/round.ts`, `one-question.ts`, `wait.ts`, `unanswered-question.ts`, `remote-round.ts`, `supervision.ts`) | **typed in core** (`method.ts`: `parseChoices`, `questionParts`, `questionShape`, `entryQuestions`, `numberOfLine`, `questionBody`, and `outsideFences`, `openFence`, `fencedLines` for the code fences a block is read outside of); the orchestrator holds none of it and draws it | the same |
| Verdict line (`<repo>#<pr> <head7> — <verdict> — blocking: <file:line, …\|none> — report: <path>`) and its limit on an agent's message to its orchestrator (`VERDICT_LIMIT`) | orchestrator | pr-review (the loop's exit), norms (`check_done`), in a session the orchestrator spawned | **typed in core** (`verdict.ts`: `verdictLine`, `reportPathOf`, `shorten`); the orchestrator's module cuts or refuses an agent's longer message (orchestrator 0.104.0, pr-review 0.10.0, norms 0.6.0) | the same |
| `deck.json` | orchestrator | Stream Deck (outside) | versioned JSON, a view of the state store held byte for byte by a golden test; each session writes it only when it differs from the file, and the minute's refresh is the machine's (orchestrator 0.98.11) | the same format, a view of the state store, one writer, rate-limited |
| Session name shapes (`Orch:`, `Agent:`, `Audit:`, `Coord:`; the former `Orch :` still read) | orchestrator | statusbar, bugs-bot, implement | defined in `core` (`names.ts`: `parseSessionName`, `roleOf`, `sessionName`, `currentSessionName`), read there by implement and the orchestrator's `dispatch-record.ts`, `hooks/naming.ts`, `hooks/move.ts`, `hooks/session-name.ts`, `hooks/stop-gate.ts` and `sleeping.ts`; the launcher (`iterm_agent.py`) builds its shapes from the generated `names.json` (version 1: the role words and the subject's pattern), tested on the same names as core (`scripts/contracts.test.ts`); still re-implemented in `coordinator.sh`, bugs-bot's `hooks/core.ts` and statusbar's `statusline.sh` | one definition in `core`, read by every plugin |
| Round files (`round/*.json`): questions, answers | orchestrator | the orchestrator alone | private; github no longer reads them (github 0.18.0, orchestrator 0.99.0) | private |
| Consent records (`consents/<owner>/<name>/<entry>.json`): the operator's answer to a round question that asks their consent, the question, the subject (repository, pull request, `e2e-waiver`, `norms-waiver`, `e2e-exemption`, `auto-merge` or `auto-deploy` with its environment) its sender declared with `declare_wait`, the time | orchestrator | github (E2E and norms waivers, E2E exemptions, `auto-merge-set`, `auto-deploy-set`) | **typed in core** (`consent-record.ts`, version 1); written by the pane's answer, the operator's answer typed in the asking session's own tab (`by: 'tab'`) and `round-close`, and by github for the answer to an E2E or norms waiver dialog (`by: 'tab'`, an entry `dialog-<session>-<ms>`), read by github in place of `round/`; the answer that grants, for every kind, is `Accorder` (core's `grants()`, beside `Refuser`): a waiver's newest answer is the waiver, `auto-merge-set` and `auto-deploy-set` with `on: true` need it, and a tab answer writes a record only when it names that one choice | the same |
| PR records (review, norms, e2e) | github | orchestrator, norms, pr-review | **typed in core** (`pr-record.ts`, version 1), the producer of each kind declared there, and the orchestrator's `accepted` review over a failed one at the same head (`ACCEPTANCE`, github 0.20.0, orchestrator 0.103.0), so github names no consumer; github's Python writer loads the generated `pr-record.json`; tested across both (`scripts/contracts.test.ts`); the review verdict is computed from the review agents' findings blocks (pr-review 0.7.0); github refuses a review record written by the session that pushed the head (github 0.14.0), and implement launches its reviewer as another session (`/implement:review`, 0.5.0); a check plan `{pr, plan}` only from the orchestrator's `mcp__orchestrator__review` | the pushed heads known across sessions and machines, not only by the session that pushed |
| Readiness (`readiness.ts`): what Ready means at a pull request's head, who holds each condition (the github gate the records, GitHub the required CI check), the `Ready` label the gate puts on all of them and a merge or leaving draft needs, the severities that block a review, the needs a check plan may give and a required review's rounds with their cap (`reviewNeed`, `reviewRounds`), what a new head voids | core | github (the gate's `missingEvidence`, the plan's needs, `protect-apply --require-ci` through `readiness.json`), pr-review (blocking severities, the rounds cap as its `MAX_PASSES`, a plan's rounds), orchestrator (the plan's schema), method (a pointer from « Done means ready ») | **typed in core** (`readiness.ts`, version 1), written as `readiness.json` for github's Python engine; the workflow's job `ci` is the check it names (`scripts/contracts.test.ts`) | the same |
| Learning event (`<config>/<plugin>/journal/<id>.json`, one file per event): a fact that vanishes with the session (a refusal, a finding, the operator's structured answer, an escape), with pointers to the records that hold the rest, never a command, a prompt's words or a finding's summary; version 2, the audit trail: which session, dispatch row, pull request and goal belong together (`link`), each step's start or end (`step`: implement, review, correction, ci-wait, merge), each review verdict (`review`) and the decision on each finding (`decision`), each declared wait (`wait`), the method's failures (`failure`) | each plugin that writes one, in its own directory | the learning plugin, and telemetry's index (the declared kinds, `learning-audit.json`) | **typed in core** (`learning.ts`: version 1 read by `parseLearningEvent`, version 2 by `parseAuditEvent`, either by `parseJournalEvent`, each refusing a field its version does not name; `learningEvent` and `auditEvent` build one, `appendEventOver` (hooks) and `appendEvent` (scripts) write it and prune the journal past the window, retention and count, `prunable`), written as `learning.json` and `learning-audit.json` for the other languages; the orchestrator writes both versions: its guards' refusals by stable code, its review verdicts and decisions, the github tool's pull requests opened and merged, declared waits (hooks/audit.ts), and the dispatch record, CI waits and successions (`skills/orchestrator/scripts/lib/audit.ts`) | the same, each writer tested against core's reader (`scripts/contracts.test.ts`) |
| `mcp__github__gh` commands (`pr-create`, `pr-gate`, `pr-readiness`, `pr-plan`) and the `mcp__github__record` tool | github | orchestrator, norms, pr-review (`pr-plan`: the rounds of an orchestrated loop, the cap when unreadable) | declared by norms and pr-review (`>=0.20.0`, when the record tool took `dir`) and the orchestrator (`>=0.20.0`); a record written and a `pr-gate` or `pr-checks` read put `Ready` when the pull request is ready (core's readiness contract), so the orchestrator runs `pr-gate` when its CI watch says green: `ci-watch.sh`'s green line ends with that call, `next: mcp__github__gh pr-gate {"pr": <n>}` (« What the caller does ») | the same |
| Launcher CLI (`iterm-agent.sh spawn`) | orchestrator | bugs-bot, implement, telemetry (`spawn` and `close` command lines read from the Bash calls it observes: `--title`, `--tier`, `--model`, `--effort`, `--permission-mode`, `--auditor`, `--coordinator-successor`; `hooks/collect.ts` `orchestrationOf`) | the script's path and the `spawn` line are core's (`orchestration.ts`: `LAUNCHER`, `launcherOf`, `spawnArgv`), read by implement, bugs-bot and the orchestrator's own hooks; implement locates the orchestrator through the host's install record (core `recordedInstallPaths`), bugs-bot through its own reader of that record (`bugs_bot/plugin_path.py`) | a versioned argument set |
| Launcher bench opening (`iterm-agent.sh bench-open`, `close --bench --socket`) | orchestrator | the outcome evals (`scripts/lib/outcome`) | `bench-open` prints `socket=`, `tty=` and `session=`; `close --bench` ends the home server it names; both refuse a directory or a socket outside the bench the caller passes; the home server's socket (under `<bench>/tmux`) and the orchestrator's working directory sit inside the bench, while the launch script, the prompt, the servers' file and `close.log` go to the launcher's state directory | a declared command with a versioned argument set |
| Declared wait in a session's transcript (`declare_wait` tool call with `{kind, blocks}`, plus `question` for an `operator` wait, kinds `operator`, `tool`, `done`, `deferred`), and the `Decision: <question> → <choice>` lines the outcome evals' brief asks of an orchestrator | orchestrator | the outcome evals (`scripts/lib/outcome/transcript.ts`) | the tool's name and kinds are re-declared in `transcript.ts`, as the orchestrator's `hooks/wait.ts` and `stop-gate.ts` declare them; the `Decision:` line is the brief's own convention (`orchestration.ts`) | the kinds typed in `core`, read by both |
| Dispatch record command line (`dispatch-record.sh <sub> <record> [<id>]` and its `--class`, `--tier`, `--model`, `--effort`, `--head`, `--verdict`) | orchestrator | telemetry (read from the Bash calls it observes, `hooks/collect.ts` `orchestrationOf`) | the subcommand set documented in the header of `dispatch-record.sh`, re-read as words; an unknown subcommand is recorded as given | the record's events published by its owner |
| `ListAgents` text | host | bugs-bot | parsed once in core (`orchestration.ts`: `selfOf`, `peersOf`) | the host's structured data, once it publishes one |
| Environment: `ORCHESTRATOR_SPAWNED`, `ORCHESTRATOR_CONTEXT_GATE*`, `CLAUDE_GITHUB_ROOT` | orchestrator / github | norms, telemetry (`ORCHESTRATOR_SPAWNED`) | **named in core** (`env.ts`); `npm run deps` refuses another plugin's variable core does not declare; norms reads `ORCHESTRATOR_SPAWNED` through `isSpawned`; the gate's variables reach other plugins only as the measure file's `gate_tokens` | the same |

## Installer permission rules

The rules an installer writes (conventions, « Permissions and security »). Each names its own
script, which validates every argument.

| Rule | Plugin | Validation the script performs |
|---|---|---|
| `Bash(<install>/skills/iterm-agents/scripts/iterm-agent.sh spawn --open *)` | orchestrator | permission mode in an allowlist (program, orchestrator defect D2), directory checks |
| `Bash(bugs-bot:*)`, printed for the operator to add, never written (`bugs_bot/doctor.py` `ALLOW_RULE`) | bugs-bot | the CLI's own parser: one of its fixed subcommands; `deploy_check` runs the project's command split into words, without a shell, and only when the project file is the operator's alone (`bugs_bot/agent.py`) |
