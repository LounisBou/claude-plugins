# Review round

## Review rounds run in disposable sessions

Reading costs context, and judgment stays in one place: the heavy reading goes to a session spawned for the round and closed when it is judged, the verdict stays with you. One rule: **one session per round, closed at the end — the next round gets a fresh session and a fresh brief**, never a standby tab.

- **Adversarial review of a delivery.** Spawn a REVIEW agent (read-only on the code; its brief is filled by its fields, never retyped, by `review-brief.sh`, which names them when run bare: never open the template) whose job is to read the delivery with the readers you sized for it, verify their findings and write them in two levels, critical and important (its brief §4), ONE line to you. **You size the round by the work** — its nature, volume, scope and criticality: from the review session's own single reading to several read-only sub-agents of the type `orchestrator:lens`, one lens each (correctness, security, tests, silent failures, types, comments, spec conformity); the brief states the choice and why (`--lens`, `--size`, `--reason`). The index the review agent writes is `--index <path>`: a new file of its own, never the implementer's report (`review-brief.sh` refuses an existing path, and `--report`). The implementer's report is `--delivery-report <path>`, named in the brief for its self-review lines and its E2E line. When the delivery claims no visible or built effect, the brief may ask its `drift` verdict quoted or rerun. **Where the plan requires a norms check (`norms: required`), the norms lens is the project's own tool wherever the project ships one**: the review session runs that norms check over the diff under review and takes its report as the lens's findings, each carrying the rule or the precedent it cites; where the project ships none, the lens reads the norms file by hand and the report says which of the two it was. Report-only either way — its fix path is never taken. You decide each finding through `mcp__orchestrator__review`, and the ONE corrective brief names the index, never copies a finding. The delivery arrives self-reviewed (`method:lifecycle`): the review session reads the self-review lines of the implementer's report first, and you size its readers by risk — full for security, guards and data, one pass for docs and small fixes.

### The deepest method, from the first round

If the real proof is to build the artifact and use it (walk the interface, drive the API, load the data), do it in the review round itself, against a control built from the previous head. A reading now and a build afterwards is a second review round. The round's readers — inside its ONE review session, never the implementer's and never one session per lens — read a copy pinned at the head under review, a detached worktree of your own checkout (`workspace.sh pin <source> <round> <head>`), never a clone, which is for a writer; `workspace.sh delete` takes it when the round is judged. **A review round is a fresh reader, not a fresh lens**. The repair is read by the gate and a reader pinned at its head over the kept items only, never a full second round: a round's sharpest defect sits inside the fix it ordered. **The correction round is closed only when every kept item arrives with the reading that closes it** — or with a sentence saying what the fixtures cannot show.

### The cost of a round

A round's wall clock is the cold start, the verification gate and the decision round trips, in that order; never buy speed with the gate. Three levers, all generic:

- **Batch by round, not by artifact.** The disposable unit is the ROUND, not the pull request, the file or the thread. Several small artifacts that share one working directory belong in one round: one cold start, one gate, one report. Split when they need different working directories (the one-writer rule), when one is large enough to deserve its own reading, or when a verdict on one would change the scope of another.
- **Overlap the gate with the writing.** The gate is the longest step and depends only on the last commit: it starts the moment that commit lands, the agent writing its report, diffs and reply text while it runs, then stating the result as DONE with its exit code.
- **Skip the assessment step for items already judged.** When you have already ruled, or when the item is mechanical and its precedent is named (a rename, a literal, an annotation copied from a cited file), the brief names those index entries DECIDED and the agent applies them.

The scoped-run rule of `templates/agent-phase-brief.md`, « Rules », binds this round's gate too.
