# Review

Read before dispatching a review or comments round, before a verdict on a delivery, before you record a review or correction round, or tell the operator a pull request is ready, and before the rebase that comes before the ready. Both readings — the evidence review and the project's norms check — are owed on every agent-produced pull request, small ones included; the rules a verdict never crosses — one review round and one correction round, ready as the github gate's — are the first section below; the rest is how the round is run.

## Thresholds a verdict never crosses

They hold at every step of the loop, whatever the rest of this file adds.

**One review round, one correction round, and you close it.** That is your process on a pull request you dispatched; rounds of review repeated until nothing is left are the operator's own, when he runs reviews by hand, and never yours. The review round: ONE review session, its readers sized by you, and the project's norms check in it: the norms check's exit code is not a verdict, its findings come back like any others — verify each on the artifact, keep or drop by pertinence AND severity — and item 9 governs the ones existing code contradicts. The triage: yours — every finding verified on the artifact, kept only when it must necessarily be fixed, dropped when it is not pertinent, and every dropped item named in one line with its reason. The correction round: ONE phase carrying the kept items and nothing else, which you verify yourself on the artifact — the diff, the tests that decide, and a mutation where the verdict rests on a test you have not seen fall. Then it is done: no review of the correction round, no further round, no over-correction.

**Ready is the github ready gate's, at the current head** (`method:lifecycle`, « Done means ready »): you never declare it. Before it can hold: the review round and its norms check done, the correction round made and verified, the E2E line settled (item 14), `dispatch-record.sh ready` green — and the branch rebased first, conflicts resolved by you (on the main branch, and each pull request of a stack on the one below it), since a rebase moves the head and every record counts only at the head it names. The gate puts `Ready` once the four hold at that head (a record, or the call `ci-watch.sh`'s green line ends with: run it); `pr-readiness <n> ready` names what is missing. Once `Ready` is on, you tell the operator « ready », with its E2E line; never `pr-ready` outside auto-merge.

## Review on evidence

### The checks

For each delivery, run yourself (read-only):
1. Git layout: branches, bases, commit messages; diffs disjoint between stacked PRs.
2. Diff stats: no forbidden files, no scope creep.
3. Domain artifacts field-by-field against the spec, including checking house patterns the spec may have missed (spec omissions are YOUR findings to fix in the spec).
4. Grep the diff and commit log for what the workflow artifacts policy forbids (`references/briefs.md`, standing rules).
5. Sample-read one core file and one test file for norms conformance.
6. Re-derive the agent's proofs: a verification procedure the agent invented may have a hole (e.g. a schema diff that also captures pre-existing drift, so demand differential baselines).
7. **Treat claimed command output as a claim — cleanup claims included.** Re-run the one command whose result decides your verdict, or check the artifact directly (`ps`, `ls`, the served page). Internal consistency of a report proves nothing.
8. **Verify literal domain values the plan supplied.** Field names, numeric bounds, enumerated catalogues: check them against the authoritative source (vendor class, protocol doc, provider), not against the plan: a shape-checking test passes the right count of wrong names.
9. **A norms file can be aspirational.** Before accepting a norms finding, check whether existing code contradicts it: a rule the codebase widely violates is a convention question for the user, not a defect in the new diff. Enforce it on new code, do not manufacture findings from it.
10. **Ask of every test and every guard: what does it NOT read, and what would it still read if the behaviour were gone?** A gate green over what it does not read is the most common shape of false proof: a guard that counts its own prose, a test that passes on the code it was written against, a hold made tautological by the repair beside it. When the verdict rests on a test you have not seen fall, mutate it on purpose: break the behaviour, watch the test fall and name the right defect, restore.
11. **A fall under load is a finding until its mechanism is named.** « Flaky, passes alone » is a conclusion nobody earned; re-running until green is the habit by which a real fall elsewhere gets dismissed as this one. Demand the mechanism (shared state, ordering, a wait shorter than the drawn duration), and if the run must be repeated, say in the same breath that the re-run removed the load the failure needed.
12. **A pull request that creates or substantially modifies a frontend surface is not read on its diff alone.** A missing or unrelated screenshot is a finding. Before the verdict, dispatch `orchestrator:screenshots` at the standard tier with `<owner/repo>#<n>`, its head sha, what the diff changes on screen and the checklist file, `${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/references/screenshot-checklist.md`. You never open the batch yourself: on doubt about one capture, open that one only. Relay its lines « per the screenshots agent »: an `unreadable:` line is an image not audited. A defect on a capture is a finding, and the pull request is not ready. Record its reply with `dispatch-record.sh audit <record> <id> --head <sha> --images <n> [--defect "<text>"]...`, and at the verdict `dispatch-record.sh surface <record> <id> --ui <owner/repo>#<n>`, `--minor <reason>` or `--none`, for every open pull request of the batch: `ready` refuses the rest.
13. **A diff that changes an existing test's assertions is read first.** Most edits that game a suite land in its test files. Each such change is a finding, kept unless the brief or a ruling ordered it: a weakened expectation, a removed case, a widened tolerance, a test skipped.
14. **Every pull request carries an E2E test the reviewer replays, or says plainly it has none.** The report carries `E2E: <test path(s)> — <command> — passed` — a backend test against the service brought up in a container, a frontend one a Playwright test committed in the project's test tree — or `E2E: none — <reason>`. Replay the test, or judge the reason; a report with no E2E line is a finding, and the pull request is not ready: silence is not allowed. A pull request with `E2E: none` is not ready on your word. For the github gate, record `not-applicable` with the reason when no file holds runtime; a repository the operator exempted needs nothing. Otherwise tell him « no E2E test — <reason> »: it is ready once he has validated it ready without one, unless he has exempted every pull request of your session. `ready --e2e` records his validation (`--e2e-waiver "<his words, dated>"`) or that exemption (`dispatch-record.sh exempt <record> --e2e "<his words, dated>"`).

### The record

**And the round ends on the record, not on memory.** The review round is recorded with `dispatch-record.sh review <record> <id> --head <sha> --norms tool|none`, the correction round you verified once with `dispatch-record.sh fixed <record> <id> --head <sha>`, and `dispatch-record.sh ready <record> <id> --head <sha> --e2e "<the E2E line>"` checks, at the head in front of you, what the github gate does not read: the surface, the screenshots' audit and the E2E line (`orchestrator:model-routing`, « The record », says what each records and refuses). It is your pre-check, never the ready. The gate's own records are written by their producers at the head they read (github's `engine/REFERENCE.md`, « Records »): the review that counts is one made at the current head, so a head your correction round moved is reviewed there before the gate can hold. Whether your triage was right and whether the correction was verified stay yours.

### Checks, in one background watch

**Checks, in one background watch.** When a pull request you own is opened or its head moves, start `ci-watch.sh <n>` (`skills/orchestrator/scripts/ci-watch.sh`, by the absolute path of the plugin's installed copy) with `run_in_background` and a timeout of 7 200 000 ms: one per pull request, never two. Its exit wakes you with one line, and the script's header says what each line asks of you, « What the caller does ». Never a foreground watch, never a loop on `gh pr view` or `gh pr checks`, never a wait for MERGED of your own; an agent never watches CI, and no session is spawned or rotated to watch it.

### The rebase, before the ready

**The rebase, before the ready.** A rebase or merge of the base whose conflicts are mechanical (no behaviour decided) is yours, done in place in a checkout and never by a spawned session; one that decides behaviour goes to a correction session. The rebase comes BEFORE the ready, which is read at the head it leaves; a rebase whose conflicts you resolved is verified like the correction round, by you — `git range-diff` against the verified head shows the resolution and nothing else, and the test suite runs on the new head. **The squash-merge trap**: once a lower pull request of a stack is squash-merged, its commits exist on the main branch under no name you can rebase over; the next branch is rebased by replaying ONLY its own commits onto the main branch — `git rebase --onto <main> <old head of the lower branch> <branch>` — never the lower branch's original commits, which come back as conflicts or as duplicates. The rebase is pushed with `--force-with-lease=<branch>:<sha read>`, the lease on the head you read; it is the one force this rule allows.

### The deepest method, from the first round

**Where the deepest method applies: from the FIRST round.** If the real proof is to build the artifact and use it (walk the interface, drive the API, load the data), do it in the review round itself, against a control built from the previous head. There is no later round to build in: a reading now and a build afterwards is a second review round. The round's readers — inside its ONE review session, never the implementer's and never one session per lens — read a copy pinned at the head under review, a detached worktree of your own checkout (`workspace.sh pin <source> <round> <head>`), never a clone, which is for a writer; `workspace.sh delete` takes it when the round is judged. **A review round is a fresh reader, not a fresh lens**. The repair is read by you, not by a second round: a round's sharpest defect sits inside the fix it ordered, which is why your verification of the correction round reads the artifact, never the report alone, and mutates what the verdict rests on where you have not seen that test fall. **The correction round is closed only when every kept item arrives with the reading that closes it** — or with a sentence saying what the fixtures cannot show.

### The verdict message

Verdict message back: findings list (fix items), approved decisions (say so explicitly), and answers to every question the agent flagged. Approve or dispatch a correction; never silently accept. A stale figure during a repair round is not a finding.

## Review rounds run in disposable sessions

Reading a delivery costs context, and judgment must stay in one place. So the heavy reading goes to a session spawned for the round and closed when the round is judged, and the verdict stays with you. Two shapes, one rule: **one session per round, closed at the end — the next round gets a fresh session and a fresh brief**, never a standby tab.

- **Adversarial review of a delivery.** Spawn a REVIEW agent (read-only on the code, brief from `${CLAUDE_PLUGIN_ROOT}/templates/agent-review-brief.md`) whose whole job is to read the delivery with the readers you sized for it, collect their reports, and send you ONE consolidated report: per finding, file and line, severity, the evidence that shows it, the proposed fix. **You size the round by the work** — its nature, volume, scope and criticality: from the review session's own single reading to several read-only sub-agents of the type `orchestrator:lens`, one lens each (correctness, security, tests, silent failures, spec conformity); the brief states the choice and why, in `{{ROUND_SIZE}}` and `{{ROUND_SIZE_REASON}}` — for a single reading, `{{LENSES}}` and `{{LENS_TIER}}` read `none`. When the delivery claims no visible or built effect, the brief may ask its `drift` verdict quoted or rerun. **The norms lens is the project's own tool wherever the project ships one**: the review session runs that norms check over the diff under review and takes its report as the lens's findings, each carrying the rule or the precedent it cites; where the project ships none, the lens reads the norms file by hand and the report says which of the two it was. Report-only either way — its fix path is never taken. It is the one session allowed to dispatch readers; it writes and posts nothing. You then verify every finding on the artifact, keep only what must necessarily be fixed, drop what is not pertinent and name each dropped item with its reason, and refuse over-corrections: a fix that adds noise, churn or scope to silence a low-severity remark is a finding against the review, not against the code. Routine items you settle yourself; what you cannot settle alone (design, scope, a disagreement between the reviewer's evidence and the spec) goes to the operator with its context, never as a bare list. Kept items become ONE corrective brief for an implementer session. The review agent is stood down and its tab closed once its report is judged.
- **Publishing under the operator's name — nothing outward-facing is published without the operator's approval, and a fix needs no words.** A reply on a review thread, a comment on an issue, any text that lands under the operator's name in front of a colleague: the orchestrator may draft it, never authorise it. Approval comes from the operator and from nobody else, and an approval given for one text is not an approval for the next. And most such texts should not exist: **a thread closed by a change is answered by the change** — the diff says what was done, and a paragraph restating it is noise the reviewer has to read. Reply only when something must be said that the code cannot say: a refusal and its reason, an answer to a question, a decision taken elsewhere. Resolving a thread is not publishing and stays the orchestrator's call.
- **Processing review comments on a pull request.** Spawn a COMMENTS agent (brief from `${CLAUDE_PLUGIN_ROOT}/templates/agent-comments-brief.md`) that assesses every open thread with evidence from the codebase and sends you each assessment BEFORE acting, agreement included. You re-verify the evidence. Agent agrees and you agree: fix and resolve (or resolve alone when the fix already landed) without asking the operator. Anything less on either side: you evaluate, and ask the operator only when the call is theirs. The agent commits locally, one commit per fix, and never pushes: you read the local tree, then say « push » (a plain push, never a force). Then stand it down and close its tab. When the operator has named how the round is presented (a skill's methodology, a format), every assessment reaches him in that format, one item at a time, and the orchestrator reads that format before the first item (SKILL.md, principle 3).

The named address, the measured context near the gate and the STOP-and-ask clause apply to these sessions as to any other.

### The cost of a round

A round's wall clock is rarely the work. It is the cold start, the verification gate and the decision round trips, in that order — and the gate is the one you must never buy speed with. Three levers, all generic:

- **Batch by round, not by artifact.** The disposable unit is the ROUND, not the pull request, the file or the thread. Several small artifacts that share one working directory belong in one round: one cold start, one gate, one report. Split when they need different working directories (the one-writer rule), when one is large enough to deserve its own reading, or when a verdict on one would change the scope of another.
- **Overlap the gate with the writing.** The gate is the longest step and it depends only on the last commit, not on the prose. It starts the moment that commit lands, and the agent writes its report, its diffs and any reply text while it runs, then states the result as DONE with its exit code. A brief that sequences « report, then gate » pays the gate twice in wall clock. Where the host caps a foreground call and backgrounds the run, the agent inspects the process and reads the exit code from the captured file — it never ends a turn waiting, and it never reports a run as « going » when the process is gone.
- **Skip the assessment step for items already judged.** Assessment-before-action exists for items that need judgment. When you have already ruled, or when the item is mechanical and its precedent is named (a rename, a literal, an annotation copied from a cited file), the brief carries a DECIDED findings list and the agent applies it. Do not make an agent argue a case whose verdict is already written; do not let it apply one whose verdict is not.

None of this is bought by shortening the verification. The gate is the cheapest step to cut and the most expensive to have cut: a scoped selection must cover the tests of every file the change touches, not only the tests of the feature, and a change to a signature, a constructor or a service definition is never gated by a scoped run — those break callers no scoped path visits. Nor does a local coverage figure stand for the remote gate: the same command has read differently there, and the remote gate is the authority.

## Depth vs scope

- **Depth vs scope**: completing an ordered fix on its adjacent case (same rule, same class of failure) is YOUR call and belongs in the same corrective phase. New functional scope is the USER's call: relay, never decide. **Arbitrations are relayed with their context**: what the thing is on the screen or in the data, the two readings, and what each costs — never a bare identifier.
