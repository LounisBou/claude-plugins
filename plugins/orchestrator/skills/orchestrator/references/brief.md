# Brief

Read before planning phases or writing a brief — a phase brief, a correction round's, a review or comments session's, a rotation's or your own succession's: how it is built, the standing rules every prompt carries, the lint it passes before its spawn, and the tier its dispatch names.

## Agent prompt recipe

Write it to a file named by its subject (`<briefs dir>/<subject>.md`), then let `iterm-agent.sh spawn --brief <path> --orchestrator "<your exact ListAgents name and reference>"` build the startup prompt and spawn the fresh session in the same move (see « The agents' lifecycle is yours » in `references/agents.md`). Start from `${CLAUDE_PLUGIN_ROOT}/templates/agent-phase-brief.md`; a rotation resume brief starts from `agent-rotation-brief.md`, your own succession brief from `orchestrator-succession-brief.md`. **The path must be one the fresh session can open on the machine it runs on, and it must survive until the phase is reviewed** — never only in your context, never only in a container's temporary directory. Whether the file is committed follows the repository's own policy on workflow artifacts (see standing rules); state that policy in the prompt, do not let the agent pick.

**`spawn --brief` lints the brief before any tab exists, and a finding warns on stderr — the launch goes on.** `${CLAUDE_PLUGIN_ROOT}/skills/orchestrator/scripts/brief-lint.sh <path>` flags what a script can see: an unfilled placeholder, an unexpanded variable, a path absent from this machine, a second session reference, a background run, an over-long succession brief, and an implementer brief with no address, non-goals list or STOP-and-ask clause. What it cannot read is whether the scope is right, whether the contracts are the ones the next phase consumes, or whether the tier fits the work: a green lint is not an approved brief, it is a brief with none of the faults a script can see. A spawn with no brief (`--prompt`, for a session that needs none) is not linted; run the script by hand first when one is worth writing anyway.

Its parts, in order:

1. **Required reading**, ordered: spec → plan (global constraints + their phase) → project norms → named reference files for house patterns.
2. **Environment**: exact working directory, things to verify (not rebuild), branch to create and from where, and the **state-verification commands** the agent runs before acting (current head, what landed, what is in flight) — the agent verifies the state, it does not believe it.
3. **Scope**: deliverables copied from the plan, contracts/signatures **verbatim**, plus an explicit non-goals list ending with: "if you believe something outside this list is needed, STOP and ask the orchestrator first".
4. **Method**: TDD, incremental conventional commits, project quality gate before PR, its coverage run early — deferred minor findings turn into blockers at the gate. **A repair lands with the test that fails when it is reverted** — a fix held by nothing returns with its sign turned round.
5. **Forbidden list** (see standing rules below).
6. **Communication protocol — the orchestrator's address is NAMED in the prompt, never discovered.** Write your session's exact `ListAgents` name and reference, as they print (e.g. `project-70 [a1b2c3]`), into the prompt. A name pattern is not an address. Then: report on start and on each push; a question goes to the orchestrator and the work goes on (`method:lifecycle`, « Questions to the operator »); a blocker (STOP + proposed resolution) or the final report ends the turn on the method's status line (`method:lifecycle`, « Reports »), which the module relays; the full report in `{{REPORT_PATH}}` (`<briefs dir>/report-<subject>.md`), the message its verdict line, worded as the templates under `templates/agent-*-brief.md` word it.
7. **Delivery**: draft PR opened `Not Ready` (`pr-create --draft`), imposed title, description shape. Delivery ends at the push: the suite green locally on the final head, the pull request opened (in a project whose method opts into auto-merge, delivered as that method says), then the final report (pull request number and head sha) and the stand-down. **Figures (counts, sizes, timings) are written ONCE, on the final head** — a number re-measured every round is stale before the round ends.
8. **Resource envelope**: kill what it started, delete what it built, **and prove it with `ps` and `ls`** before reporting; the project's own limits on a shared machine, where its method writes them. **Scratch lives in the session's own host scratchpad directory**, never in a directory the brief invents, and the agent does not delete it: the close that deletes its checkout takes it (`agents.md`, step 4).

## Every dispatch names its tier

At the dispatch gate you read the agent's fill on `/orchestrator-status` against the gate the module reports, then choose the model/effort pair the work needs. `orchestrator:model-routing` is the aid to that decision: the table informs, you decide, and you write your choice and its reason in the brief. The tier and the reading that chose it go into the brief, so the agent can tell you when the work outgrew them; the brief names the servers the session was given where it names the tier, so an agent never reaches for a tool it was not given.
