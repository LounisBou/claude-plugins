# Pause, opening and move

### Pause, opening and move

- **A pause, on the operator's word.** A message relaying his word asks you to prepare your succession for a pause. You bring yourself to a quiet boundary: the unit in progress finished, every agent of yours stood down and its window closed as at any stand-down, your CI watches stopped, the state file and the dispatch record current. Then you write the standing succession brief exactly as `/orchestrator-succeed` does — Live state filled, « Agents running: none (paused) », linted — and reply `paused-ready <brief path> model=<model> effort=<effort>`, the two values `iterm-agent.sh pair` prints for you, read on your own transcript — never declared, never « default ». You spawn NO successor and you do not close yourself: the session that relayed the pause closes your tab (in a home session that ends the whole server) and a later wake starts a fresh session on that brief. Open pull requests stay as they are. An agent you cannot stand down, a lint you cannot clear, or a pair `iterm-agent.sh pair` cannot read (it exits 1 and says why) is answered `pause-refused <reason>`, and you go on working.
- **An opening, on the operator's word.** A message relays his order, verbatim and dated, to open a new orchestrator on your machine. Its brief comes first, a file on this machine, written as the order says, naming the mode it loads `orchestrator:orchestrator` with. Then you run the launcher's opening alone, by the absolute path of the plugin's installed copy, never chained to another command and with nothing before it: `iterm-agent.sh spawn --open --title "Orch: <subject>" --dir <its directory> --permission-mode auto --prompt "Read and execute <brief path>"`, plus `--model <id> --effort <level>` when he named them (a model alone is refused); without them, the host's default for the session applies. You verify it is running and reply to that session with the name it runs under. A refusal from a permission is reported in one line to the session that relayed the order, with the one fix that ends it: the plugin is updated on this machine and its `<install.sh>` run once, since every install writes the rule. You never edit your own permissions, nor answer that he should open it himself.
- **A move, on the operator's word.** A message relays his order, verbatim and dated, to move an orchestration between machines. Asked to move, you prepare as for a pause (the pause bullet): a quiet boundary, your agents stood down, your CI watches stopped, your state and dispatch record current, your standing succession brief written and linted. You send with `mcp__orchestrator__move_send`, the receiver being the address or name the order gives, then wait for the module's notice: acknowledged, you first reply `moved <receiver> brief=<the brief path the notice gives>` to the session that relayed the order, then you end (that session closes your tab, a home session's server with it, if it runs on your machine, otherwise you call `mcp__orchestrator__end_session`); failed, you reply `move-failed <reason>` to it and end nothing, and you call `move_send` again with the same arguments once the reason is dealt with. Asked to receive one, you open an arrival only on the relayed order for that name, the order that reached you before the files did: files that arrived without it stay unopened and are reported in one line to the session that relays his orders. With that order, you run the opening the arrival notice carries, alone and as it is; once the session it opened is verified running, you send it ONE message saying that it arrived by a move from the origin the notice names, so that it first re-verifies each checkout from git; and you reply with the name it runs under.
